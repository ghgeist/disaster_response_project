# Storm Signal — Product Demo Tightening Plan

## Framing (What this *is*)

Storm Signal is a **product‑ish demo** that proves a simple but non‑obvious claim:

> Small, fast, traditional ML models can still deliver real product value — especially when they’re wrapped in good UX and used as decision tools by humans *and* AI agents.

This is *not* an attempt to showcase cutting‑edge NLP research. It is a demonstration of **taste, speed, and end‑to‑end product thinking**.

---

## Primary Optimization Target: Delight

We are explicitly optimizing for **delight**, not technical novelty.

Delight here means:

* Instant feedback (feels fast)
* Visual clarity (feels legible)
* Confidence (feels trustworthy enough)
* Low cognitive load (feels obvious how to use)

Outdated NLP techniques are acceptable *as long as the experience is excellent*.

This is a conscious trade‑off.

---

## Core Product Insight (Single Sentence)

> A ~4MB model can power a fast, attractive, useful decision tool — and that’s often the right trade‑off.

Secondary narrative (optional, not front‑and‑center):

* Traditional ML models can act as **cheap, reliable signal generators** for AI agents.

---

## The Golden Path (Frozen)

This project supports **one** primary end‑to‑end path:

1. User pastes or types a message
2. App returns:

   * Top predicted categories
   * Confidence scores
   * A clear, friendly explanation of what happened
3. User immediately understands:

   * What the model thinks
   * Why it’s useful
   * That it’s fast and lightweight

Anything not serving this path is *suspect by default*.

---

## Surfaces & Boundaries

### Surface A — Demo Surface (Public, Polished)

* Flask app UI
* Stable inference API
* Curated example inputs
* Screenshots + live demo link

This surface must:

* Be stable
* Be visually clean
* Hide internal complexity

### Surface B — Lab Surface (Private / Secondary)

* Training scripts
* Experiments
* Evaluation notes
* Dev logs
* **Agent-assisted training scaffolding** (kept, but clearly separated)

This surface may be messy, but:

* It is clearly marked as internal
* It does not leak into the demo UX

---

## README as Contract (Not a Tour)

The README should answer **exactly three questions**:

1. What does this demo show?
2. How do I run the demo?
3. What’s optional / behind the scenes?

Anything else belongs in `docs/` or is removed.

If the README claims something that cannot be demonstrated in 5 minutes, it is wrong and should be edited or deleted.

---

## Legacy & AI‑Thrash Cleanup Strategy

Cleanup here is about **clarity, not amnesia**. Valuable ideas may be archived rather than deleted.

### Kill / Archive Criteria

Delete *or archive* code that:

* Is not required to run the golden path
* Represents alternate training or inference flows not actively used
* Was generated by AI but is not fully understood or trusted
* Duplicates functionality

**Archive instead of delete** when:

* The idea is sound but not currently active (e.g. agent‑driven training loops)
* You may want to resume work later

Bias toward **deletion or archiving over refactor**.

### Acceptable State

* Some experiments are gone
* Some ideas live only as notes or archived scripts
* The demo works reliably and looks great
* Future‑You can tell *what mattered* at a glance

That is a win.

---

## UI/UX Design Constraints

The UI should:

* Feel more like a *tool* than a dashboard
* Avoid exposing internal model mechanics unless they add delight
* Emphasize speed, simplicity, and clarity

The UI should *not*:

* Explain NLP theory
* Show training metrics
* Reveal internal scaffolding

---

## Sequencing (Very Important)

1. Freeze the golden path
2. Remove or disable obvious sources of sprawl
3. Make the demo delightful and stable
4. **Stabilize the “6‑month return” spine (docs + commands + decisions)**
5. Only then revisit experimentation ergonomics (optional)

Do **not** redesign UX and refactor internals at the same time.

---

## 6‑Month Return Constraint (Non‑Negotiable)

The repo must be clear enough that future‑you can return in ~6 months and quickly answer:

* What is the golden path?
* What’s the current best model artifact?
* What are the exact commands to run demo / train / evaluate?
* What are the highest‑leverage next experiments?

This implies one durable “spine” inside `docs/`:

* **Current state** (what works today)
* **Decision log / changelog** (why it is this way)
* **Next experiments queue** (what to try next, with expected upside)

Example high‑leverage queued experiment (already known):

* **Re-translate tweets** (likely performance improvement)

---

## Open Questions (Deferred)

These questions are intentionally **left open** and will be resolved later, ideally by interacting with the existing AI agent scaffolding inside the repo rather than speculating upfront.

* What level of autonomy should AI agents have when training or modifying ML models?

  * Merely running predefined scripts and reporting results?
  * Modifying configs and pipelines within guardrails?
  * Proposing and implementing experiment changes end‑to‑end?

* What agent tooling already exists in the repo today, and what is aspirational vs. real?

* What is the minimal agent contract worth preserving so this idea remains legible in 6–12 months?

These questions should **not** block demo cleanup or UX work.

---

## Success Criteria (Binary)

This plan succeeds if:

* A reviewer can understand and enjoy the demo in under 30 seconds
* The app feels fast and intentional
* The repo feels honest about what it is and is not
* Future‑you can re‑enter the project in 30 minutes and run the demo + locate the next experiment

Anything beyond that is optional upside.
